Here's the deployment plan for `rag/` to Vercel, optimized for many concurrent users with low latency.

## Architecture decisions

| Concern | Choice | Why |
|---|---|---|
| Backend runtime | **Vercel Python Functions on Fluid Compute** (default) | Keeps FastAPI as-is; Fluid reuses warm instances across concurrent requests → no per-request cold start |
| Region | **`sin1` (Singapore)** | Lowest latency for SG users + closest to Gemini |
| Index storage | **Pre-built JSON shipped with the deploy** | TF-IDF index built once at build-time, loaded into memory on cold start (~ms) — never re-parses PDFs at runtime |
| API key | **`GEMINI_API_KEY` env var** (server-side) | Users don't paste their own key; one shared backend key, lower friction |
| Frontend | **Vite static build** served from Vercel CDN | Sub-100ms globally |

The current code re-parses PDFs with pdfplumber on every cold start (~5–10s). That's the #1 latency killer in a serverless context. Pre-building the index removes it.

## Step-by-step

### 1. Restructure for Vercel
Vercel expects:
```
rag/
├── api/
│   └── index.py          # FastAPI entrypoint (exports `app`)
├── backend/
│   ├── rag_engine.py     # existing
│   └── index.json        # NEW: pre-built TF-IDF index
├── public/assets/*.pdf
├── scripts/
│   └── build_index.py    # NEW: builds index.json at deploy time
├── src/                  # React app
├── requirements.txt      # NEW: fastapi, pdfplumber, requests, pydantic
├── vercel.json           # NEW: routes + region + build config
└── package.json
```

### 2. Pre-build the index (`scripts/build_index.py`)
Runs locally or in CI. Walks PDFs, builds the TF-IDF index, serializes vocab/idf/doc_tfs/documents to `backend/index.json`. Commit the JSON.

### 3. Modify `rag_engine.py`
Add `load_index(path)` and `save_index(path)` methods on `SimpleTFIDF` so cold starts hydrate from JSON instead of running pdfplumber.

### 4. Create `api/index.py`
```python
from backend.main import app  # FastAPI instance
```
Vercel auto-detects the `app` symbol and serves it.

### 5. Create `requirements.txt`
```
fastapi
pdfplumber       # only needed if you ever re-index in prod; can drop
requests
pydantic
python-dotenv
```
Dropping `pdfplumber` shrinks the function bundle significantly — only the builder script needs it.

### 6. Create `vercel.json`
```json
{
  "buildCommand": "npm run build",
  "outputDirectory": "dist",
  "functions": {
    "api/index.py": { "memory": 1024, "maxDuration": 60 }
  },
  "regions": ["sin1"],
  "rewrites": [
    { "source": "/api/(.*)", "destination": "/api/index" }
  ]
}
```

### 7. Frontend tweaks
- Remove the "Enter API Key" UI (or keep as override). Default flow uses server key.
- `fetch('/api/query')` already works — Vercel routes it to the function.

### 8. Deploy
```
cd C:\Users\admin\rag
npm i -g vercel              # CLI not installed
vercel login
vercel link                  # link to new project
vercel env add GEMINI_API_KEY   # paste once; available in prod
python scripts/build_index.py   # builds backend/index.json
vercel --prod
```

### 9. Performance tuning after first deploy
- **Watch cold starts** in Vercel dashboard → Functions tab. With Fluid Compute, you should see <500ms p95 once warm.
- **Cache Gemini responses** for identical queries via Vercel Runtime Cache or an in-memory LRU keyed on `(query, mode, model)` — same questions from different users return instantly.
- **Drop relevance-filter parallel calls to Gemini** for low-latency mode — they fire 5 extra API calls per query. The TF-IDF top-5 is usually good enough; only run the filter when the user asks for higher quality.
- **Use `gemini-2.5-flash-lite`** for query expansion (cheap, fast) and reserve `gemini-2.5-flash` or `pro` for final generation.

### 10. Multi-user concurrency
Fluid Compute handles this natively — one instance serves multiple concurrent requests on the same Python process, so the in-memory index is shared. No extra config needed. If you outgrow it, move the index to Vercel Edge Config or Upstash Redis.
